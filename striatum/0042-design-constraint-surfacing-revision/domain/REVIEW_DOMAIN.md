### Review Findings for RFC 0031: Design Constraint Surfacing Revision

**Context:** This review assesses RFC 0031 against `docs/design/kayak_hull_design_constraints.md`, RFC 0006, RFC 0029, `AGENTS.md`, `PRD.md`, and `USER_GUIDE.md` to confirm its domain correctness and implementability without creating false precision or unsupported kayak design claims.

**Summary:** RFC 0031 is a well-structured and prudent revision that successfully narrows the scope of RFC 0029 to a safe and implementable first pass. It clearly defines `enforced`, `advisory`, and `unsupported` validity semantics, aligning them consistently with existing design constraints and the overall project vision. The proposal to implement additive structured metadata for these findings across various outputs (CLI, web, desktop, sweeps, reports) will significantly improve user transparency regarding design choices and their current validation status. This approach effectively mitigates the risk of false precision by explicitly stating the current limitations of certain parameters and evaluations.

**Findings:**

*   **Alignment with RFC 0006 and `kayak_hull_design_constraints.md`:** The classification of constraints into `enforced`, `advisory`, and `unsupported` directly corresponds to the existing design principles laid out in RFC 0006 and the `kayak_hull_design_constraints.md` document.
    *   **Enforced:** The requirement for positive dimensions and `beam_wl_m <= beam_oa_m` is consistent with RFC 0006's established invariants. RFC 0031 correctly identifies these as model-level enforcements.
    *   **Advisory:** The surfacing of warnings related to L/B_wl, Cp, and displacement guidance, as well as class preset drift, is a direct implementation of RFC 0006's deferred advisory partials. This provides crucial guidance without limiting user freedom, as intended.
    *   **Unsupported:** The explicit designation of fields like `LCB_frac`, `rocker_bow_m`, and `rocker_stern_m` as `unsupported` until their geometry or evaluation is fully honored is a critical step in preventing false precision. This aligns perfectly with `USER_GUIDE.md`'s current caveats about such parameters (e.g., `LCB_frac` being "reserved and not yet honored").
*   **Pragmatic Scope Revision (RFC 0029 vs. RFC 0031):** RFC 0031's decision to narrow the scope from RFC 0029 is sound. RFC 0029 was broad, aiming for full surface parity and complex metadata propagation simultaneously. RFC 0031's additive approach, focusing on structured metadata and preserving existing string warnings as a compatibility wrapper, allows for a more controlled and safer implementation. This also aligns with the project's iterative development philosophy, as evidenced by `AGENTS.md` and the various workflow definitions.
*   **Prevention of False Precision:** The clear distinction between `enforced`, `advisory`, and `unsupported` levels, along with the explicit non-goals in RFC 0031 (e.g., not treating advisory warnings as proof of seaworthiness or race performance), robustly prevents overclaiming design validity or performance. This is crucial for maintaining the integrity of the generative CFD pipeline and managing user expectations, as outlined in `PRD.md`.
*   **Consistency with Project Mandates:** The RFC aligns well with the `PRD.md`'s audience (designers wanting fast, honest feedback) and its "delivered today" vs. "roadmap" sections. It also respects the "out of scope" boundaries in the PRD and the current project direction described in `AGENTS.md`, which notes that some constraints are only partly surfaced.

**Conclusion:** RFC 0031 is a well-reasoned and necessary revision. It clarifies the project's stance on design constraint validation, provides a clear path for surfacing this information transparently, and avoids making claims beyond the current capabilities of the generator and evaluation tools. It is domain-correct and implementable without introducing misleading information.

**Verdict intent: accept**
