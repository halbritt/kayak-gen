# Domain Review: Workflow 0034 - Watertight Volume Mesh Handoff

This review focuses on the domain aspects of the watertight volume mesh handoff workflow, examining generated-body readiness, self-intersection blockers, volume-mesh evidence, profile-scoped `cfd_ready` semantics, and fixture boundaries, in preparation for implementation.

## Generated-body readiness and Self-intersection blockers

*   **RFC 0016 (`closed-volume-geometry`)** and **RFC 0023 (`watertight-volume-mesh-handoff`)** are foundational for this aspect. The readiness of a generated body hinges on successful self-intersection detection and resolution.
*   **Finding:** The workflow relies on robust self-intersection checks. The implementation (`kayakgen/eval/closed_volume.py` and related tests) must clearly demonstrate that generated bodies are free of self-intersections. Specific parameters or thresholds for what constitutes an 'unacceptable' intersection need to be explicitly defined and validated.
*   **Evidence Required:** A clear process or test case demonstrating how self-intersections are detected and either prevented or reported as blockers.

## Volume-mesh evidence

*   The successful handoff requires that the generated mesh is not just a surface, but a valid volume representation.
*   **Finding:** It is critical to ensure that the mesh generated by `kayakgen/eval/mesh_package.py` (and tested by `tests/test_mesh_package.py`) correctly represents a watertight volume. The definition of "watertight" in this context (e.g., zero-volume holes, consistent face normals) must be precisely articulated and verifiable.
*   **Evidence Required:** Documentation or test output confirming the mesh's volumetric integrity. This could include checks for manifoldness, normal consistency, and absence of topological defects.

## Profile-scoped `cfd_ready` semantics

*   **RFC 0010 (`cfd-ready-mesh-contract`)** and **RFC 0015 (`cfd-solver-dispatch-and-jobs`)** define the semantics of `cfd_ready`.
*   **Finding:** The interpretation of `cfd_ready` needs to be clearly scoped to specific CFD profiles or simulation types as defined in the RFCs. It is essential that the workflow ensures the mesh meets the criteria for the intended CFD application (e.g., boundary layer requirements, element quality for specific solvers). The implementation (`kayakgen/eval/cfd/jobs.py`, `kayakgen/cli/main.py`) must correctly translate these profile requirements into actionable checks.
*   **Evidence Required:** Clarity on how `cfd_ready` is determined and verified against profile-specific requirements. Are there distinct `cfd_ready` states for different solvers or analysis types?

## Fixture boundaries

*   The presence of evaluation modules and test files (`tests/*`) suggests a reliance on fixtures for validation.
*   **Finding:** The boundaries of these fixtures, particularly in relation to the `cfd_ready` definition and generated body acceptance, need to be well-defined. For example, what specific test cases constitute a "fixture" for validating the `cfd_ready` status, and how do these relate to the broader acceptance criteria?
*   **Evidence Required:** Documentation or clear definitions of the test fixture coverage and how they map to the overall acceptance criteria for a mesh handoff.

Overall, the workflow scaffold appears to address key aspects of watertight mesh handoff. However, explicit verification of the evidence and precise definitions for each readiness criterion will be crucial during the implementation phase.
