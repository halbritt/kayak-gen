# High-Angle Stability Model Vote

Vote: Fixed-Trim Generated-Body V1 (Option B)

## Decision Sentence

Accept the v1 high-angle `GZ` model as a fixed-upright-trim hydrostatic comparator over `generated_hull_plus_deck_closed_body_v1` after RFC 0024 generated-body diagnostics pass: default heel grid `0..90 deg` by `5 deg` with caller-supplied strictly increasing grids echoed exactly, hull-fixed passive load-case CG with recorded component masses/LCG/KG, per-heel sinkage/displacement solve with reported residual and unsolved longitudinal-moment residual, closed waterline clipping and capping diagnostics distinct from body diagnostics, additive per-heel `status`/residual/iteration metadata on `GZCurve` before any partial curve reaches a user surface, grid-bounded summary metrics, sealed-body deck/flooding warnings, and explicit no-safety/no-seaworthiness/no-design-fitness/no-validation language; until this model is implemented and tested behind RFC 0024 gates, every real generated-kayak `gz_m`, `righting_moment_nm`, `max_gz_m`, `heel_at_max_gz_deg`, `range_positive_stability_deg`, and `area_under_positive_gz_m_deg` continues to return unavailable with `None` summaries.

## Evidence

- The decision question itself is enumerated in RFC 0043's Proposal section: body profile, heel grid, heel transform/sign, trim policy, sinkage/displacement solve, CG convention, waterline clipping, and deck/flooding assumptions must all be answered before any real generated-kayak `GZ` work begins (`docs/rfcs/0043-high-angle-gz-successor.md:70-100`). Option A defers the question; the panel is expected to answer it.
- RFC 0024 already fixes the evidence gate: only a generated kayak closed body with passing closure, positive signed volume, zero blocking boundary/nonmanifold edges, no blocking self-intersections, matching `source_hull_hash`/coordinates/units/tolerances, and a stability-compatible closure policy can ever emit real kayak `GZ` (`docs/rfcs/0024-high-angle-gz-generated-body-handoff.md:44-65`). Synthetic explicit bodies remain `fixture_only` and cannot be promoted (`docs/rfcs/0024-high-angle-gz-generated-body-handoff.md:62-65`).
- RFC 0022 already supplies a concrete body that meets the profile requirement: `generated_hull_plus_deck_closed_body_v1` is a generated hull-plus-deck closed body with cap surfaces, join strips, waterline metadata, source hash, policy, and diagnostics, kept separate from display STLs (`docs/rfcs/0022-generated-closed-body-construction.md:46-60`, `docs/rfcs/0022-generated-closed-body-construction.md:110-127`). Adopting it avoids inventing a second body concept before the existing one is exhausted.
- The roadmap classifies the high-angle stability track as `blocked` and lists exactly the model bullets the decision must resolve before implementation can start (`docs/ROADMAP.md:51-53`, `docs/ROADMAP.md:71`, `docs/ROADMAP.md:191-207`). Batch G's exit criteria explicitly forbid numeric secondary-stability output until those gates pass. A vote that does not answer the bullets does not unblock the track.
- The runtime already enforces the unavailable boundary and explicitly leaves CG model, trim policy, and deck/flooding unresolved: `kayakgen/eval/stability.py` returns RFC 0024 unavailable envelopes with the default `0, 5, ..., 90` grid and the `high_angle_gz_generated_body_solver_not_implemented` warning even when generated-body diagnostics pass (`kayakgen/eval/stability.py:1-8`, `kayakgen/eval/stability.py:38-44`, `kayakgen/eval/stability.py:617-641`). The `GZCurve` contract already rejects legacy unproven curves and demands coherent availability/body provenance/grid/arrays/summaries/assumptions/warnings (`kayakgen/eval/contract.py:109-165`). Option B's gates therefore line up with code that already exists.
- Independent external check, accessed 2026-05-14: Guillemot Kayaks' kayak-stability explainer treats kayak righting-arm curves as CG/CB separation over heel with the paddler bolt-upright and no active correction, and emphasizes CG height as material ([guillemot-kayaks.com/kayak-stability](https://guillemot-kayaks.com/kayak-stability)). This supports v1 using hull-fixed passive CG and disclosing it as an assumption rather than an active human-response model.
- Independent external check, accessed 2026-05-14: Maxsurf Stability documents both fixed-trim and free-trim large-angle modes as named options, along with explicit loadcase displacement/VCG/LCG, downflooding angle, and water-on-deck/damage choices ([maxsurf.net/stability/Bentley/Maxsurf Stability Manual.htm](https://maxsurf.net/stability/Bentley/Maxsurf%20Stability%20Manual.htm)). Fixed-trim is a legitimate named comparator; free-trim is a stronger but separate mode that should not be silently substituted.
- Independent external check, accessed 2026-05-14: 46 CFR 28.570 specifies intact-stability righting-arm calculations and, in one allowed method, requires free trim until trimming moment is zero at each heel, along with downflooding considerations ([law.cornell.edu/cfr/text/46/28.570](https://www.law.cornell.edu/cfr/text/46/28.570)). Fixed-trim v1 is therefore explicitly a comparator, not a regulatory equilibrium curve, and the unsolved longitudinal-moment residual is material and must be reported.
- Independent external check, accessed 2026-05-14: PIAS guidance notes that heel-angle resolution must be sufficient where curves bend sharply, and that wider heel ranges are needed for asymmetric cases ([sarc.nl/images/manuals/pias/htmlEN/stab.html](https://www.sarc.nl/images/manuals/pias/htmlEN/stab.html)). This supports grid-bounded summaries by default for a 5-degree grid, with interpolation reserved as a named successor mode.
- Independent external check, accessed 2026-05-14: DELFTship's stability documentation includes righting-arm and downflooding/deck-edge submersion curves as distinct outputs ([delftship.net/manuals/professional/introduction/stability](https://www.delftship.net/manuals/professional/introduction/stability/)). For kayak-gen's sealed full-deck body without a cockpit-opening or flooding model, the appropriate response is explicit warnings, not hidden defaults.
- Independent external check, accessed 2026-05-14: VTK's `vtkCutter` documents plane-cutting as a defined geometric intersection with a cut function ([vtk.org/doc/nightly/html/classvtkCutter.html](https://vtk.org/doc/nightly/html/classvtkCutter.html)), while `vtkFillHolesFilter` is documented as topology-sensitive and capable of failing on nonmanifold/open surfaces ([vtk.org/doc/release/4.0/html/classvtkFillHolesFilter.html](https://vtk.org/doc/release/4.0/html/classvtkFillHolesFilter.html)). Trimesh's mass-property and `is_watertight` semantics make the same point: volume and centroid integration require closed evidence ([trimesh.org/trimesh.base.html](https://trimesh.org/trimesh.base.html)). These support treating per-heel waterline clipping as a first-class diagnostic separate from body-level closure, with explicit failure rather than heuristic filling.
- Independent external check, accessed 2026-05-14: IMO's Intact Stability framing puts `GZ` inside criteria, weather, and flooding limits ([imo.org/en/OurWork/Safety/Pages/IntactStability-Default.aspx](https://www.imo.org/en/OurWork/Safety/Pages/IntactStability-Default.aspx)). This is not a kayak standard, but it confirms that geometry-based righting-arm output is not a safety, seaworthiness, or capsize-recovery claim and must carry that disclosure.

## Why Rejected Alternatives Lose

- Option A (Keep Real GZ Unavailable) is the correct runtime state today and remains in force until v1 lands behind gates, but it is not an answer to the panel question. RFC 0043 explicitly asks the panel to record body profile, heel grid, trim policy, CG convention, waterline clipping, residuals, convergence warnings, and deck/flooding assumptions (`docs/rfcs/0043-high-angle-gz-successor.md:70-100`). Voting A leaves Batch G blocked without naming a model, so the project would need a second panel before any work can scope.
- Option C (Free-Trim Per-Heel) is physically stronger and matches the eCFR free-trim path, but it couples sinkage and trim, multiplies non-convergence modes, requires solved trim/iteration/moment residuals at every heel, and would land before kayak-gen has even proved per-heel waterline clipping over a generated body. Maxsurf documents free trim as a named separate mode rather than the only mode ([maxsurf.net/stability/Bentley/Maxsurf Stability Manual.htm](https://maxsurf.net/stability/Bentley/Maxsurf%20Stability%20Manual.htm)). C should be the named successor once B's per-heel pipeline is in place.
- Option D (Flooding/Downflooding/Active Paddler) is out of reach because the accepted body profile has no cockpit opening, compartments, water-on-deck progression, paddler volume, or active human-response model. Adding any of these requires new geometry profiles, load-case fields, and a validation RFC.
- A hull-only or cockpit-cut stability body loses for v1 because it would introduce a second closed-body concept before `generated_hull_plus_deck_closed_body_v1` has been used at all (`docs/rfcs/0022-generated-closed-body-construction.md:46-60`). It is a legitimate successor if sealed full-deck curves prove misleading at high heel, but not a v1 decision.

## Implementation Gates And No-Claims Language

Gates that must be implemented and tested before any real generated-kayak `GZ` value reaches CLI, sweep, comparison, desktop, or web output:

- Body profile: `generated_hull_plus_deck_closed_body_v1` v1 only, gated on full RFC 0024 diagnostics (closure, positive signed volume, zero blocking boundary/nonmanifold edges, no blocking self-intersections, matching `source_hull_hash`/coordinates/units/tolerances, stability-compatible closure policy). Explicit synthetic bodies remain `fixture_only` and ineligible for `body_ref` (`docs/rfcs/0024-high-angle-gz-generated-body-handoff.md:44-65`).
- Heel grid: default `0, 5, ..., 90` degrees; caller-supplied strictly increasing grids echoed exactly in both `heel_grid_deg` and the computed `heel_deg`; no precision implied beyond the supplied resolution.
- Trim policy: fixed upright trim solved once for the load case; per-heel sinkage/displacement-equilibrium solve only; unsolved longitudinal-moment residual reported per heel point; free-trim per-heel reserved as a named successor mode, not a default.
- CG convention: hull-fixed passive CG for hull, paddler, and cargo, with component masses, LCG, KG, and any default-KG synthesis recorded as a warning. World-fixed or actively bracing paddler CG is out of scope.
- Waterline clipping/volume integration: heeled waterplane cut produces a closed capped submerged body before volume/CB acceptance; clipping/capping diagnostics are recorded per heel point and are distinct from body-level diagnostics; failure marks the heel point failed rather than heuristic-filled.
- Per-heel status metadata, additive on `GZCurve` before any partial curve reaches a user surface: `heel_deg`, `status` in {`computed`, `non_converged`, `clipping_failed`, `skipped`, `unsupported`}, sinkage/waterplane offset, `trim_angle_deg`, `trim_policy`, `displaced_volume_m3`, `displaced_mass_kg`, `load_mass_kg`, `displacement_error_kg` and relative residual, `load_cg_world_m`, `buoyancy_cb_world_m`, `gz_m`, `righting_moment_nm`, `longitudinal_moment_error_kg_m`, tolerance names/values, iteration count, max iterations, and per-point warnings.
- Summary metrics: `max_gz_m`, `heel_at_max_gz_deg`, `area_under_positive_gz_m_deg`, and `range_positive_stability_deg` derived only from `status == computed` points; grid-bounded by default; interpolation deferred to a named successor mode. Any missing or failed point forces summaries to `None` or to an explicit partial/grid-bounded label.
- Required warnings whenever a real curve is emitted: `sealed_deck_profile_no_cockpit_opening`, `deck_immersion_assumption`, `flooding_not_modeled`, `downflooding_not_modeled`, `active_paddler_response_not_modeled`, `not_seaworthiness_or_safety_claim`, plus diagnostic-derived warnings such as `heel_point_non_converged`, `waterline_clipping_failed`, `generated_closed_body_not_available`, and `fixture_only_body_not_user_facing` (`docs/rfcs/0024-high-angle-gz-generated-body-handoff.md:97-110`).
- Any gate failure returns unavailable with `None` summaries; placeholder, fixture-derived, or heuristic values for `gz_m`, righting moments, or summary metrics remain forbidden (`docs/rfcs/0043-high-angle-gz-successor.md:95-100`).

No-claims language that must remain in force in this decision, in any successor RFC, in implementation docs, and in user surfaces once v1 lands:

- v1 is an unvalidated geometry-based hydrostatic righting-arm comparator, not a calibrated, validated, or measured-correlated stability model.
- v1 is not a final prediction, seaworthiness, safety, capsize-recovery, downflooding, design-fitness, optimization-objective, or production-CFD-readiness claim.
- The sealed full-deck body does not model cockpit openings, compartment flooding, water on deck, or progressive downflooding; results in regions where these would matter remain caveated regardless of computed value.
- Fixture-only math tests cannot satisfy user-facing stability claims, sweep ranking, or comparison summaries; this decision does not authorize promoting any `fixture_only` curve.
- This vote authorizes a model design only. It does not authorize emitting any real generated-kayak `GZ` value, summary metric, ranking, sweep score, or comparison badge until the gates above are implemented and tested under RFC 0024.

## Confidence

High. The local evidence spine (PRD, USER_GUIDE, ROADMAP, RFCs 0011/0014/0022/0024/0043, and the current `kayakgen/eval/stability.py` and `kayakgen/eval/contract.py`) and the external primary sources (Guillemot, Maxsurf, eCFR, IMO, PIAS, DELFTship, VTK, Trimesh) converge on the same answer: fixed-trim hydrostatic righting-arm curves over a passing generated closed body are a legitimate v1 model when their assumptions are disclosed, and free-trim/flooding/active-paddler models belong to named successors. The remaining uncertainty is downstream — whether the sealed full-deck body proves misleading at high heel, and whether a future kayak-envelope measured source justifies validation — and is correctly carried as open questions rather than as a blocker on this vote.
