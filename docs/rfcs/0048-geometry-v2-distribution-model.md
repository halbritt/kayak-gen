# RFC 0048: Geometry V2 — Distribution Model

Status: proposed
Date: 2026-05-16
Context: Phase 6 of `ARCHITECTURE_RECOMMENDATION_PLAN_2026-05-16.md`. The
current `HullGeometry` lofts a single legacy geometry (parametrized by
length, beam, draft, Cp, Cm, deck-flatness, parallel-mid-body, rake)
with a small number of derived controls. `docs/design/kayak_hull_design_constraints.md`
calls for an expressive enough geometry model to honor explicit rocker,
LCB targets, deadrise, chine radius, bow flare, freeboard distribution,
and multiple cross-section families. This RFC scopes a successor without
removing the existing geometry kind.

## Problem

The current loft is a single, implicit longitudinal distribution shaped
by a small set of scalar form coefficients. Several controls the
`docs/design/kayak_hull_design_constraints.md` document treats as design
levers (`rocker_bow_m`, `rocker_stern_m`, `LCB_frac`) are recorded on the
`Hull` record as reserved fields with no loft effect today. The loft also
does not parametrize cross-section family: every section is the same
sinh-shaped curve scaled by half-beam and draft. Designers asking for a
hard-chine or multi-chine surfski cannot get one from kayakgen today.

Bolting more scalars onto the existing loft is the wrong fix. The loft's
underlying assumption is that the hull shape is generated by an implicit
function of `x`, `Cp`, `Cm`, and `deck_flatness`. Reverse-engineering an
explicit rocker curve from that implicit function is fragile, and the
resulting hull rarely matches the operator's intent.

Geometry V2 proposes an *explicit distribution model*: the hull is
specified by named longitudinal distributions (half-breadth at the
waterline, draft/keel profile, section-area distribution, deck/freeboard,
LCB target, rocker) and a chosen cross-section family. The loft then
follows the distributions instead of inferring them from scalar form
coefficients.

## Goals

- Add a second geometry kind, `geometry_kind="distribution_v2"`, that the
  `Hull` model admits alongside the existing `geometry_kind="lofted"`
  (today's default).
- Expose explicit, implemented controls for:
  - bow rocker, stern rocker;
  - LCB position;
  - max-beam longitudinal position;
  - deadrise angle (constant or distributed);
  - bilge/chine radius;
  - bow flare;
  - freeboard distribution.
- Support multiple cross-section families:
  - round (today's sinh-shaped curve);
  - shallow arch;
  - shallow V;
  - deep V;
  - hard chine;
  - multi-chine.
- Build one canonical *closed body* first; derive open hull/deck STL
  inspection surfaces from that canonical body so the closed-body
  diagnostics chain (RFC 0021 + RFC 0023 + RFC 0040 + RFC 0045) does not
  need a separate code path.
- Cross-check hydrostatics by section integration and triangle/closed-body
  integration; the two must agree within a documented tolerance.
- Keep old hulls valid: any existing `Hull` JSON loads, evaluates, and
  exports STLs identically to today under the
  `geometry_kind="lofted"` path.
- Migration examples and side-by-side tests.

## Non-Goals

- No new claim state, no new readiness level, no new evaluator semantics.
- No change to existing `lofted` hulls' STL output (byte-equality
  pinned by `tests/test_golden.py`).
- No web/desktop UI changes in v1 of distribution_v2; the new controls
  surface through the CLI / sweep / search specs first.
- No automatic conversion of a `lofted` hull into a `distribution_v2`
  hull (the implicit-to-explicit direction is lossy; offer a tool, not
  an auto-migration).
- No surrogate / generative hull-shape model.
- No CFD-side change.
- No deprecation of `lofted`. Both kinds coexist until a future RFC
  reduces the surface.

## Dependencies

- `kayakgen/model/hull.py:Hull` — extends with `geometry_kind` field
  (default `"lofted"`).
- `kayakgen/model/geometry.py:HullGeometry` — abstract over distribution
  vs lofted shape generation.
- `kayakgen/eval/closed_volume/generated_body.py` (Phase 3C target) —
  the generated-body builder calls `HullGeometry.section_for_closed_body`,
  which is now public. The v2 geometry implements the same accessor.
- `kayakgen/eval/hydrostatics.py` — invariant: hydrostatics computed from
  v1 lofted geometry and v2 distribution geometry agree within the
  documented tolerance for hulls that are mathematically equivalent.

## Proposal

### Hull record extension

Add `geometry_kind: Literal["lofted", "distribution_v2"] = "lofted"`
to the `Hull` Pydantic model. When `geometry_kind == "lofted"`, the
existing fields (`length_m`, `beam_oa_m`, `Cp`, `Cm`, ...) are read as
before. When `geometry_kind == "distribution_v2"`, a new optional
`distribution_v2: DistributionV2Spec | None` field carries the explicit
distributions; the legacy scalar fields are echoed for reporting but do
not drive the loft.

```python
class DistributionV2Spec(BaseModel):
    model_config = ConfigDict(extra="forbid")
    waterline_half_breadth: LongitudinalDistribution
    draft_profile: LongitudinalDistribution
    section_area_curve: LongitudinalDistribution
    deck_freeboard: LongitudinalDistribution
    rocker_bow_m: float
    rocker_stern_m: float
    lcb_target_frac: float
    max_beam_position_frac: float
    cross_section_family: CrossSectionFamily
    deadrise_deg: float | LongitudinalDistribution
    chine_radius_m: float | LongitudinalDistribution
    bow_flare_deg: float
```

`LongitudinalDistribution` is a small discriminated union of:
- `UniformDistribution` (constant value),
- `PolynomialDistribution` (`a0 + a1*xi + a2*xi^2 + ...`),
- `KeyPointsDistribution` (a list of `(xi, value)` knots with cubic
  spline interpolation).

`xi` is normalised longitudinal coordinate in `[-1, 1]` (bow at -1,
stern at +1).

`CrossSectionFamily = Literal["round", "shallow_arch", "shallow_v",
"deep_v", "hard_chine", "multi_chine"]`. Each family has a documented
parametrization; the loft consults the family along with deadrise and
chine radius to produce a per-station ring.

### Loft pipeline

```
Hull (geometry_kind="distribution_v2")
  ↓
DistributionV2Geometry.section_for_closed_body(x, part)
  ↓
canonical generated-closed-body (Phase 3C generated_body)
  ↓
open hull/deck STL surfaces derived from the canonical body
```

The canonical body is the source of truth. The open inspection STLs are
*derived* from it rather than computed independently. This eliminates
the divergence today between open-loft and closed-body endpoint
treatment.

### Hydrostatic cross-check

For every v2 hull, hydrostatics is computed two ways:
- by section integration over the distribution_v2 stations;
- by triangle integration over the canonical closed body.

The two must agree within a documented tolerance (proposed: 0.5% for
displaced volume, 1% for waterplane area, 1% for LCB, 0.5% for GM0).

If the cross-check disagrees, the hull reports the discrepancy as an
advisory warning and the evaluation result records both values. No
silent acceptance.

### Migration tooling

A new `kayakgen migrate-geometry <hull.json>` CLI subcommand reads a
v1 lofted hull and emits a best-effort v2 distribution that matches
the v1 stations within a stated tolerance. The migration is **lossy**
and prints a warning if the round-trip discrepancy exceeds a
configurable threshold.

### What lands and what does not

Lands:
- The `DistributionV2Spec` schema and supporting distributions.
- A `DistributionV2Geometry` implementation that produces the canonical
  closed body and the derived open inspection surfaces.
- Hydrostatic cross-check + advisory warning machinery.
- Cross-section family implementations for all six listed families.
- The `kayakgen migrate-geometry` CLI subcommand.
- Side-by-side golden tests: for every existing golden hull, a v2
  equivalent that produces hydrostatics within tolerance.

Does not land:
- `kayakgen view` and `kayakgen serve` keep their current sliders for
  v1; v2 controls surface through CLI/sweep/search specs. A future RFC
  scopes web/desktop sliders for v2.
- No removal of `geometry_kind="lofted"`; coexistence is the contract.
- No automatic conversion at import time.

## Acceptance Criteria

- An existing `Hull` JSON loads and evaluates byte-identically (STL,
  hydrostatics, resistance, stability, mesh diagnostics all unchanged).
- A `Hull(geometry_kind="distribution_v2", distribution_v2=...)` hull
  produces a closed body that passes RFC 0021 self-intersection +
  RFC 0016 topology diagnostics.
- The two hydrostatic computations (section integration vs triangle
  integration) agree within documented tolerance on a parametrized
  matrix of v2 hulls (round / shallow_arch / shallow_v / deep_v /
  hard_chine / multi_chine, at three rocker amounts × three LCB
  targets).
- The migration CLI round-trip discrepancy is below the configurable
  threshold for the existing golden hulls.
- No regression in any pre-existing test.
- New evaluation surfaces (sweep, search, comparison) treat v2 hulls
  identically to v1 hulls from the caller's perspective: same
  evaluators, same record schema, same artifact paths.

## Open Questions

- What exactly is the right tolerance for the hydrostatic cross-check?
  0.5%/1% feels tight; the loft has known numerical drift at ~0.1% on
  the existing goldens.
- Should the migration CLI write the v2 record into the same file
  (rewriting the source) or into a sibling `<name>.v2.json`?
- Should cross-section family `multi_chine` parametrize chine count
  (2, 3, 4) or fix it at two chines (deck-side + bilge-side)?
- Does the deadrise field belong on `DistributionV2Spec` (constant or
  distributed) or on the cross-section family (per-family rule)?
- Should rocker be a `LongitudinalDistribution` directly, or remain two
  scalar end-values that the implementation interpolates with a chosen
  curve?
- Do we keep `bow_rake` / `stern_rake` on v2 (where they no longer
  control the loft) for backwards-compat reporting, or refuse them when
  `geometry_kind="distribution_v2"`?

## Implementation Path

1. Extend `Hull` with `geometry_kind` + optional `distribution_v2` block;
   Pydantic-validate; existing JSON loads byte-stably (no
   `distribution_v2` block means v1).
2. Add `DistributionV2Spec`, `LongitudinalDistribution` union, and the
   discriminated cross-section family enum.
3. Implement the six cross-section families as pure-Python sampling
   functions.
4. Implement `DistributionV2Geometry.section_for_closed_body` driving
   the generated-closed-body builder.
5. Derive open hull/deck STL surfaces from the canonical closed body.
6. Wire the hydrostatic cross-check; emit an advisory warning on drift.
7. Add the parametrized matrix tests.
8. Add `kayakgen migrate-geometry`.
9. Update `docs/USER_GUIDE.md` with the new field + subcommand.

## Domain Modeling

Boundary clarification. `DistributionV2Geometry` is a second
implementation of the same abstract aggregate (`HullGeometry`), not a
new aggregate root. `DistributionV2Spec` is a value object owned by
`Hull`. The new cross-section families are value objects with no
identity beyond their literal token.

Cite `DDD.md § "Adding to the model"`: this is a *strategy* refinement
over the existing `HullGeometry` service, plus a new value object
attached to the `Hull` aggregate. No new domain event, no new write
surface, no new persistent state beyond the new fields on `Hull` JSON.
